<Callout variant="warn" title="inject 可能错过一次请求">
  如果某次请求的 pre-step <strong>已经 claim 了它的批次</strong>，注入的上下文就会错过这次请求，等到下一个 step 边界。
  取消或 dispose 也可能丢弃挂起的上下文。
</Callout>

`Inbox` 的 `append`、`prepend`、`replace`、`remove`、`clear`、`splice`、`claim` 都会记录规范化的持久 `agent/inbox/spliced` 变更，并拒绝重复的 pending id。`claim(target)` 通过**纯删除 splice** 移除提议的 step 批次——所有 `next-step` 输入，加上在 turn 边界时的一条 `next-turn` 消息——并且**不发 discarded 通知**；per-message 的 claimed 通知由循环单独发出。

## 取消：cause 是类型化的同进程输入

```ts
/** Why an active agent driver was cancelled. */
type AgentCancelCause =
  | { readonly kind: 'user' }
  | { readonly kind: 'parent' }
  | { readonly kind: 'hook'; readonly reason: string }
  | { readonly kind: 'disposed' }
```

<Callout variant="rule" title="signal 不授予分类权">
  持有取消权的一方把 cause 拷进仅运行时的 <code>AbortSignal.reason</code>；
  <strong>signal 不负责给协作监听器分类</strong>。持久的 <code>turn/end</code> 把结果记为{' '}
  <code>{"{ kind: 'aborted', reason: TurnEndCancelCause }"}</code>，于是取消原因落在终态结果里。
</Callout>

`cancel` 的 `keepInbox` 选项保留排队与 steering 项：活的 turn 仍会被中止，但未开始的与挂起的工作会为后面的 turn 存活下来，并且**不记录取消性的 inbox splice**。

## Agent 的创建与所有权

```ts
/**
 * An owned agent plus its disposer, returned by AgentRegistry.create() / resume().
 * The disposer is a CAPABILITY: among consumers, only the holder can tear this agent down.
 */
interface AgentHandle {
  agent: Agent
  dispose(): Promise<void>
}
```

<Callout variant="key" title="disposer 是一种能力">
  在消费者之间，<strong>只有持有者</strong>能拆掉这个 agent。注册的 factory provider 也是结构性 owner，因为挂在某个 scope 上的 agent 依赖那个 provider 的服务 API——provider 卸载会停止并等它创建的每个活句柄结束。
</Callout>

`setup` 回调（`AgentSetup`）在两个 id 都还未发布时组合出 agent 的作用域世界：通过 `agentCtx` 注册的一切都在 `agent/created` 与第一次提示装配**之前**就存在。setup 拒绝、commit 抛错或 owner dispose 都会把这次事务回滚，两个 id 都不发布。

## initiating Agent

`ctx.agents` 携带的进程本地 initiator **就是**上面那个 `Agent`，不是另一个 frame，也不是被拷贝的身份。

<Callout variant="warn" title="环境里存在 initiator 既不证明活性也不构成授权">
  它的生命期与作用域规则由 initiator-scope 决策定义。<code>agent-loop</code> 把每个驱动跑在{' '}
  <code>ctx.agents.withInitiator()</code> 里面。
</Callout>
