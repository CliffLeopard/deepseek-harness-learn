## 三个角色

<Callout variant="key">
  一个 seam 由<strong>服务定义</strong>（声明接口）、<strong>服务实现</strong>（实现它）与
  <strong>消费者</strong>（使用它，通常是一个给模型用的工具）三个角色构成。
  一个包可以兼任多个角色，但<strong>单独一个角色不叫 seam</strong>；新增一项能力意味着把三个角色都设计出来。
</Callout>

## 为什么换一个实现就改变整个产品

<Callout variant="note" title="来自 docs/architecture.md">
  "Filesystem and subprocess providers share one execution world, so pointing them at a remote
  sandbox moves Bash, PTY, and LSP with them, with no provider forks."
</Callout>

文件系统与子进程的实现**共享同一个执行世界**。把它们指向一个远程沙箱，Bash、PTY 与 LSP 会一起跟着搬过去，而且不需要为任何 provider 开分支。

## 沙箱：一个 seam 如何约束另一个 seam

`ctx.sandbox` 的用法与其他 seam 不同：消费者**把自己即将 spawn 的确切 argv 交出去**，同世界的后端在一个 per-call 策略下把它包起来，并报告实施结果。

<Flow
  dir="col"
  nodes={[
    { title: 'bash-sandbox / terminal-bash', sub: '消费者', kind: 'plain', tone: 'neutral' },
    { title: 'ctx.sandbox', sub: '交出即将执行的 argv', kind: 'service', tone: 'rose', edge: 'confine(argv)' },
    { title: 'sandbox-local', sub: '同世界后端', kind: 'plugin', tone: 'amber', edge: '包裹' },
    { title: '被包裹的 argv + 实施报告', kind: 'plain', tone: 'lime', edge: '返回' },
    { title: 'ctx.subprocess spawn', kind: 'io', tone: 'neutral', edge: '真正执行' },
  ]}
/>

`ctx.sandboxPolicy` 是**部署默认模式 + 工作区根**的唯一归属地。只有受沙箱约束的执行器与 provider 读这个服务（工具层用它同时导出的纯 `sandbox/mode` fold）。两个会实施约束的族——bash 与 fs——都读同一个 policy，**所以它们不可能约束到不同的根**。

<Callout variant="rule" title="permission preset 是给用户看的一张表">
  <code>ctx.permissionPresets</code> 提供 <code>workspace-write</code> 与{' '}
  <code>danger-full-access</code> 两个预设，把沙箱模式与审批策略两个旋钮捆在一起。
  切换预设会写一条 <code>permission/preset</code> 事件，并贯穿到两个旋钮各自的事件。
</Callout>
