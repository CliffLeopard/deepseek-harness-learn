Cordis 只有五个概念。这五个概念搞清楚之后，`packages/` 里几乎每个文件长什么样你都能预测。

## 两种插件写法

这两种形态只解决「模块怎么被 Cordis 挂上」。写完之后怎样进产品、怎样进入一次 turn，见 [第 04 章](/docs/plugins)。

<Split>
  <Panel title="函数式插件" tone="accent">
    最常见的形态。适合只贡献 effect、不需要暴露服务的插件。

```ts
import type { Context } from '@deepseek-ai/cordis'

export const inject = ['tools', 'llm']

export function apply(ctx: Context) {
  // 每个贡献都是一个 effect：卸载时自动撤销。
  const dispose = ctx.tools.register(myTool)
  ctx.effect(() => dispose)
}
```

  </Panel>
  <Panel title="Service 子类" tone="violet">
    当插件本身要占据 ctx 上某个服务键时使用。Cordis 负责它的生命周期。

```ts
import { Service } from '@deepseek-ai/cordis'

export class MyRegistry extends Service {
  static inject = ['sessions']

  constructor(ctx: Context) {
    // 第二个参数就是它占据的服务键：ctx.myRegistry
    super(ctx, 'myRegistry')
  }
}
```

## 事件派发模式

插件之间不互相 import，靠事件通信。事件名用 TypeScript 声明合并写进 `interface Events`，**派发模式是这条事件公开契约的一部分**：它决定监听器能不能返回值、会不会被 await、能不能改写结果、能不能让后面的人不再跑。

五种模式对应五个派发方法。监听一律 `ctx.on(name, handler)`；发出去的时候必须用对上的那个方法——`emit` 事件不能拿去 `waterfall`。新增 harness 事件要在 JSDoc 里写 `@mode`，生成目录会核对声明和实际派发点。

<Callout variant="key">
  先问「监听器是观察、改写、并发收尾，还是抢一个答案」。选错模式，后面的人要么改不了结果，要么默默把整条链吃掉。
</Callout>

  <code>session/event</code> 再看 <code>event.type</code>，不要去 <code>ctx.emit('turn/start')</code>。

### emit：广播，只观察

`ctx.emit(name, ...args)` 按注册顺序**同步**调用监听器，不等待它们返回的 Promise，也不收集返回值。适合「这件事已经发生了，告诉大家」。

**使用场景**

- 事实已经冻结，监听器改不了结果：`session/event`、`tools/result`、`agent/error`、`agent/status`、`tools/change`。
- UI、转录、遥测、日志插件。不要在 emit 里做「允许 / 拒绝」——没有返回值通道，也没有短路。

```ts
ctx.on('tools/result', (exec, result) => {
  console.log(`${exec.name} -> ${result.isError ? 'error' : 'ok'}`)
})
```

异步监听器里的失败会被吞掉或另行记录，**不能**拦下后续监听器。需要「所有人都做完才继续」时用 parallel。

### waterfall：包装或短路

`ctx.waterfall` 是 **around-middleware**，不是「按顺序通知一圈」。每个监听器拿到 `(...args, next)`：调用 `next()` 把控制权交给下一个人（以及最后传入的默认实现）；**不调用 `next()` 就返回，等于否决整条链**。返回值沿 `next()` 向上传，所以外层可以包装内层的结果。

这是 harness 里**策略与改写**最常用的模式：`agent/pre-step`、`agent/request`、`agent/request-error`、`llm/stream`、`system-prompt/assemble`、`tools/pre-execute` / `execute` / `post-execute`、`approval/request`。

<Callout variant="trap" title="只观察的人忘记 next()，会静默吃掉下游">
  日志、指标这类监听器<strong>必须</strong> <code>return next()</code>。只有真正拥有该决策的策略才能不调用 next() 直接返回。
</Callout>

```ts
ctx.on('tools/pre-execute', async (exec, next) => {
  if (!(await isAllowed(exec))) {
    return { kind: 'deny', reason: 'Denied by policy.' }
  }
  return next()
})

declare function isAllowed(exec: unknown): Promise<boolean>
```

派发方法本身不像 parallel/serial 那样替你 await 每个监听器；链的返回值常常是 Promise，由调用方 await。写新事件时最后一个参数是默认实现（链尾的 `next`）。

### parallel：并发做完，没有否决

`await ctx.parallel(name, ...args)` 让**所有**监听器同时跑，并等它们全部结束。没有返回值通道，也没有人能否决别人。

**使用场景**：一件事必须落到每一处之后，调用方才能继续。仓库里的例子是 `session/flush`——缓冲里的事件要进持久存储，每个监听器都是一个耐久检查点，不能像 waterfall 那样被短路。

不要用 parallel 做策略。策略需要返回值或 `next()`，那是 waterfall / serial / bail。

### serial：顺序 await，可提前结束

`await ctx.serial(name, ...args)` 按注册顺序跑，并等待每个监听器（含 async）。**第一个不是 `null` / `false` / `undefined` 的返回值成为结果，后面的人不再跑。** 没有 `next()`。

**使用场景**

- 需要「一个接一个做完，而且可以提前给出答案」的阶段。
- harness 里的 `agent/turn-stopping`：turn 即将关闭时按顺序 await 监听器。这里的处理函数返回 `void`，异议的方式是调用 `agent.steer(...)`，机器再读 inbox——**数据决定要不要再跑一个 step，所以监听器顺序改变不了结果**。不要把它写成 waterfall，它没有 `next()`。

和 waterfall 的差别：serial 不能包装下游返回值；它要么弃权（返回空），要么给出一个值并停掉后面的人。

### bail：第一个有效答案

`ctx.bail(name, ...args)` 是 serial 的**同步**版：按注册顺序跑，第一个不是 `null` / `false` / `undefined` 的返回值胜出并停止后续。派发方法本身不等待 Promise。

**使用场景**：同一时刻只能有一个人认领的同步决策。Web Client 输入机上的 `slash/input-begin-command`、`slash/input-insert-reference`、`slash/input-consume-token`、`slash/input-insert-text` 都是 bail——某个插件返回 `true` 表示已经处理了这个 token，别人不必再动。

需要 await 或允许异步认领时，用 serial，不要用 bail。

### 声明一次，模式就钉死

```ts
declare module '@deepseek-ai/cordis' {
  interface Events {
    /** @mode emit */
    'stats/report'(name: string, count: number): void
    /** @mode waterfall */
    'demo/transform'(input: string, next: () => Promise<string>): Promise<string>
  }
}
```

`ctx.on` 与 `ctx.emit` / `ctx.waterfall` / … 都会按这份签名推断。`import type {} from '@deepseek-ai/dsh-tools'` 这类副作用导入，是为了让当前文件看见别的包合并进来的事件。

循环里各扩展点挂了哪种模式，见 [第 06 章](/docs/lifecycle)；工具管线三段 waterfall 见 [第 08 章](/docs/tools)。

## vendoring 政策

`vendor/` 下的包是**固定的源码副本**，不是依赖。清单与上游 SHA 在 `vendor/README.md`。更新流程也在那里；更新后需要重新施加或退役已记录的本地修改，并重跑 `pnpm run test && pnpm run build`。

`@deepseek-ai/cosmokit` 与 `@deepseek-ai/schemastery` 通过 `pnpm-workspace.yaml` 的 `overrides` 指向 `link:vendor/...`，这样本地构建一定解析到工作区里被固定的那份源码。
