## 装配点

`ctx.systemPrompt` 是**所有给模型看的文字都从这里装配**。插件贡献四种输入，循环每个 step 调一次 `assemble()`，然后把结果渲染成完整的模型提示。

<Callout variant="key" title="为什么工具 schema 属于装配的一部分">
  「模型被告知它能做什么」<strong>是一件连贯的事</strong>，即使适配器在线上把 schema 作为一个独立字段传输。
  段落与 schema provider 是<strong>两个独立的装配输入</strong>，所以限制一个工具并不会移除独立注册的指导文本。
</Callout>


<Callout variant="trap" title="toolOrder 的两级失败时机不同">
  <strong>格式</strong>不对（缺 rest 条目、有重复）在 <strong>config 加载时</strong>抛错；
  但一个已列出却没有注册工具的名字，会让<strong>每一次 assemble() 被拒绝</strong>——也就是在第一个 turn 才暴露，而不是启动时。
</Callout>

`ToolProviderResult` 的两个字段正是为此存在：`schemas` 是本次装配里模型看得见的集合，`knownNames` 是 provider **限制前**的名字全集，用来区分「配置里写错了名字」和「一个已知工具在这个 scope 里被故意藏起来」。

## KV Cache 的代价

<Split>
  <Panel title="系统提示" tone="accent">
    只要身份、人格、变量、段落文本与顺序渲染结果完全一致，前缀就是稳定的。

    任何改动都可能**从第一个改变的系统提示 token 起**让复用失效。
  </Panel>
  <Panel title="工具 schema" tone="lime">
    只要可见 schema 集合、渲染与顺序不变，前缀就是稳定的。

    注册、限制或重排序都可能**从第一个改变的 schema token 起**让复用失效。

    限制一个工具会移除它对该 agent 的**全部 schema 成本**，但不会移除一个独立的提示段落。
  </Panel>
</Split>

## 运行时上下文与提示段落的区别

<Split>
  <Panel title="PromptSection：变成提示文本" tone="accent">
    进入系统提示，位于请求最前面。

    对 KV cache 敏感：它就是前缀本身。

    适合**稳定的指导**：工具用法、人格、策略。
  </Panel>
  <Panel title="PromptContext：变成 user-role 快照" tone="violet">
    进入模型历史，位于**保留的模型历史之后**。

    agent-loop **只在它变了或被压缩移除时**才记下完整的当前快照——没变就不必重写。

    适合**会变的事实**：沙箱策略、审批策略、委派状态、时钟。
  </Panel>
</Split>
