## 前台运行的结果：正交事实各占一个字段

```ts
/** The outcome of one completed (or killed) foreground run. */
interface ShellRunResult {
  /** Exit code; null when the process died from a signal. */
  exitCode: number | null
  /** Terminating signal (e.g. 'SIGTERM'); null on normal exit. */
  signal: NodeJS.Signals | null
  timedOut: boolean
  aborted: boolean
  // …
}
```

<Callout variant="key" title="一个进程可以既超时又 exit 0">
  因为它<strong>捕获了信号</strong>。所以 <code>timedOut</code>、<code>aborted</code>、
  <code>signal</code>、<code>exitCode</code> 各自是独立字段——调用方<strong>不会</strong>把一次被砍断的运行读成干净的成功。
</Callout>

`timedOut` 与 `aborted` 互斥：一个融合的 deadline 同时驱动执行器超时与调用方取消，所以在进程 close 之前竞态到达的超时与 abort 只报告**第一个原因**，不会两个都报。

## 逐调用的策略，而不是固定在 provider 上

```ts
/**
 * What one confined execution is allowed to touch — carried PER CALL, not
 * fixed on the provider.
 */
interface SandboxPolicy extends SandboxExecutionPolicy {
  mode: ConfinedSandboxMode
}
```

<Callout variant="key">
  两个消费者可以在<strong>同一瞬间</strong>用不同策略约束——bash 在 <code>read-only</code> 下，而一个被约束的子 agent 需要它的状态目录可写。
  一次被批准的升级重试就是<strong>一个带更宽策略的新调用</strong>，而不是去改 provider 状态。
</Callout>

`ctx.sandboxPolicy.resolve(request)` 拥有优先级与根回退，好让 bash 与 fs 不必各自重复一遍：

## 文件系统：目标身份与 read-before-edit

每个操作先把用户提供的路径解析成一个**不透明的后端目标**。消费者可以展示 `displayPath`，但**不得解析** `targetKey`（一个带品牌的不透明 id），也不得假设它是本地绝对路径。

<Callout variant="trap" title="glob / grep 不走 ctx.fs">
  <code>read</code> / <code>write</code> / <code>edit</code> 注入 <code>ctx.fs</code>。
  <code>glob</code> 与 <code>grep</code> 走 <code>ctx.subprocess.spawn</code> 加上打包的 ripgrep——它们不 inject 文件系统服务。
  所以换掉 <code>fs-local</code> 不会自动改搜索行为；搜索跟随的是执行世界里的 subprocess provider。
</Callout>

## 文件 IO 上没有超时

<Callout variant="rule">
  <code>read</code> / <code>write</code> / <code>edit</code> <strong>不接受</strong>{' '}
  <code>timeoutMs</code>，provider 契约也不武装任何 deadline。
</Callout>

对比一下：bash 与 web 消费 `@deepseek-ai/dsh-timeout`，由子进程支撑的 `glob` / `grep` 声明的 `timeoutMs` 由 `dsh-tool-call-timeout-policy` 强制——**这些都是进程支撑的，deadline 真的能杀掉工作**。

而一次本地 syscall 最多只能做到 best-effort 可中止：一个超时无法强迫进行中的 `fsync` / `rename` 停下来。所以这里放一个 `timeoutMs` 会是**一个 seam 根本无法强制的 deadline**，而且正好落在「显式优于隐式」所禁止的位置上。取消仍然通过工具执行 signal 传播，在 syscall 边界做 best-effort abort。

## 错误分类是稳定字符串

文件系统失败使用稳定的 `FsErrorCode` 字符串，由 `FsError`（一个 `HarnessError`）携带。工具注册表在错误结果上**保留 `{ name, code }`**，所以重试层、权限层与 UI 层可以分支而不必解析文本。
