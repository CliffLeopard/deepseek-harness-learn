## 一条共享的硬约束

<Callout variant="rule" title="应用形态只能是 dsh 加一个 profile">
  每一个受支持的 Node 应用都从 <code>dsh</code> CLI 加一个命名 profile 开始。
  自定义插件组合仍然是<strong>一个 profile 加若干有序的 patch 文件</strong>——而不是另一个可执行文件，也不是内联的应用树。
</Callout>

## SDK 线协议

<Callout variant="key" title="一行一条 JSON-RPC 2.0 消息">
  在调用方自己拥有的字节流上，每条消息以 <code>\n</code> 结尾。
  <strong>同时带 id 与 method 的帧是请求，只有 id 是响应，只有 method 是通知；格式错误的行被忽略。</strong>
</Callout>

<DataTable
  head={['方向', '方法', '载荷']}
  rows={[
    ['client→server', 'initialize', 'InitializeParams → InitializeResult'],
    ['client→server', 'session/prompt', 'SessionPromptParams → SessionPromptResult（持久入队收据）'],
    ['client→server', 'shutdown', '无参数 → {}'],
    ['server→client', 'session.event', 'SessionEventNotification（运行时里每一个会话，不过滤）'],
    ['server→client', 'session.status', 'SessionStatusNotification（整 agent 的 running/idle 迁移）'],
    ['server→client', 'subagent.started', 'SubagentStartedNotification'],
    ['server→client', 'subagent.finished', 'SubagentFinishedNotification（仅进程内运行）'],
  ]}
/>

错误语义也是固定的：没有注册 handler 的请求答 `-32601`，handler 失败答 `-32603`，错误响应以 `JsonRpcResponseError` 拒绝挂起的请求并**保留线上的 `code` 与可选 `data`**。`start()` 挂上流监听器，`close()` 摘掉它们并拒绝挂起请求，**但不销毁流**。

<Callout variant="trap" title="messageId 不标识后来的任何东西">
  <code>SessionPromptResult.messageId</code> 标识的是<strong>被排队的那条用户消息</strong>——
  它不标识后来的助手消息、turn 结束，也不标识 prompt 的结果。
</Callout>

握手也是硬的：服务端在初始化期间**解析确切路由**，并在握手成功之前**拒绝 `session/prompt`**。所以缺失的适配器、不可用的模型或不支持的 reasoning effort **不可能回退到构造器默认值**。

<Callout variant="warn" title="stdout 只承载 JSON-RPC 帧">
  所以一个部署<strong>不得</strong>组合任何 stdout logger。
  <code>dsh-sdk-jsonrpc-server</code> 用 dispose 根运行时并 exit 0 来回答 <code>shutdown</code>；
  EOF 与信号退出归应用 bin 所有。
</Callout>

## 两个 SDK 是设计上的孪生

<Split>
  <Panel title="TypeScript：dsh-sdk-client" tone="accent">
    `DeepSeekHarness` 用来 spawn 运行时、打开会话、发 prompt，并收集最终响应加上事件与通知流；`HarnessClient` 给出对协议层的显式控制。

    启动 spec 是**显式**的：调用方可以用 `dshBin` 点名运行时可执行文件，省略则解析同版本 `@deepseek-ai/dsh` 包的 bin，参数由客户端构造。

    它是纯库：**在 Cordis context 上不注册任何东西**，它 spawn 的运行时是一个完整 harness，其组合由那个运行时自己的 `cordis.yml` 决定。
  </Panel>
  <Panel title="Python：deepseek-harness-sdk" tone="violet">
    运行时 wheel 把普通的 `dsh` CLI 打包成 `deepseek-harness-runtime-bin`，客户端默认启动 `dsh --profile sdk`。

    可运行的最小示例选择随产品发布的独立 `sdk-minimal` profile；同一个运行时也打包了 `dsh web` 与它的前端资源，供单独的 CLI 使用。

    **每一次启动都要求显式选择 Harness home——Python 从不静默读取 `~/.dsh`。**
  </Panel>
</Split>

<Callout variant="note" title="Python 镜像而不 import 这些类型">
  所以改动这里的一个方法、载荷，或线上稳定的 <code>serverInfo.name</code>，都需要在<strong>同一个改动</strong>里更新 Python 一侧与 TypeScript 客户端。
  两个 SDK 都跟着这个循环走：agent-loop、会话生命周期与 <code>SessionEventMap</code> 的改动要在同一个 PR 里更新两侧的期望输出。
</Callout>

<Callout variant="trap" title="两个已知空缺">
  <strong>没有 cancel 或 session-close 方法</strong>——客户端通过关闭运行时进程来放弃一个 turn。
  <strong>server→client 请求是一个死能力</strong>——传输支持它，但服务端从不发送；Python SDK 的应答面是为将来的审批流预留的。
</Callout>

具体的降级路径：无效的正则是**不匹配**；执行器 reject 变成一个**没有退出码**的 `HookOutput`；退出 2 以 stderr 为理由阻止；其他任何失败都保持**非阻塞**。

<Callout variant="rule" title="方言之间只差一个轴">
  差异只在<strong>如何解释一个 matcher 模式</strong>：<code>claude-code</code>{' '}
  把模式解释成字面备选项或一个正则，<code>codex</code> 总是解释成一个未锚定的正则。
  所以 matcher 把 mode 作为<strong>参数</strong>，而不是把引擎复制两遍。
</Callout>

## hook/* 会话事件

`hook/invoked` 与 `hook/result` 通过声明合并进入 `SessionEventMap`，是**仅日志**记录：和 `compaction/*` 一样，它们**不是** surface 事件，也不携带 `surfaceOp`。一个 `hook/result` 通过 `handlerId` 与它的 `hook/invoked` 配对。

<Callout variant="key" title="调用与结果记录必须落在一个打开的 turn 里">
  <code>UserPromptSubmit</code>、<code>PreToolUse</code>、<code>PostToolUse</code> 与{' '}
  <code>Stop</code> 按构造就满足这个关系；而 <strong><code>SessionStart</code> 在 turn 1 之前运行，因此拿不到 hook/* 记录</strong>——它注入的上下文改为通过 inbox 投递，直到一次唤醒性投递打开一个 turn。
</Callout>

不变量伴生插件注册在 `ctx.invariants` 上，拒绝以下情况：`hook/*` 事件被追加在打开的 turn 之外、一个没有匹配 invoked 的 result、未知方言，以及非有限的 duration。

<Callout variant="warn" title="什么时候不该用 hook 桥">
  为没有参考工具对等物的定制行为——那时候应该写<strong>原生 Cordis 插件</strong>，它拥有完整的 harness API，中间不隔一层 hook 协议。
</Callout>
