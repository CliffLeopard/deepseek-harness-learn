## 关于真实 API 的立场

<Callout variant="key" title="我们就是 DeepSeek——不要节省真实 API 测试">
  一个无 key 测试只证明<strong>管道通</strong>；只有带 key 的运行才证明<strong>agent 面对真实模型能工作</strong>。
</Callout>

要覆盖：写文件的 prompt、多轮对话、工具使用、流中途取消。价值最高的是**smoke 测试**——启动一个随产品发布的 `dsh` profile、发一个 prompt、然后**检查世界**。它们抓的是「单元测试全绿、产品坏了」这一类问题，而 mock 抓不到。

<Callout variant="note" title="自跳过不是一个成本信号">
  它的作用是让无密钥 CI 与没有 key 的贡献者不被卡住。
  profile 级集成测试放在 <code>apps/cli/tests/profiles/</code>；包专属的组合与它的包测试放在一起。
</Callout>

## 三条断言纪律

<Steps
  items={[
    {
      title: '优先真实实现，而不是 mock',

        </>
      ),
    },
    {
      title: '验证世界，不是自我报告',
      body: (
        <>
          一个 e2e 断言要<strong>重跑命令或从外部重读文件</strong>；对 agent 自己输出做关键词探测会让一个作弊的 agent 通过。
          断言未被触碰的文件<strong>逐字节相同</strong>。
        </>
      ),
    },
    {
      title: '测试真实入口路径',
      body: (
        <>
          「真实入口路径」指<strong>发布出去的产物</strong>：一个包 <code>bin</code> 在<strong>纯 node</strong> 下运行构建好的{' '}
          <code>lib/bin.js</code>，暴露 tsx 会掩盖的失败——settle 竞态、模块解析、被吞掉的加载失败。
        </>
      ),
    },
  ]}
/>

<Callout variant="warn" title="一个 guard 只有在回归能让它失败时才叫 guard">
  对没有 <code>inject</code> 的插件（bundle / 组合插件），一个 Loader smoke 在 default 导出替换掉必需的具名导出时<strong>仍然是绿的</strong>——
  所以要加一条显式的 <code>expect('default' in mod).toBe(false)</code> 加上一次{' '}
  <code>unwrapExports</code> 往返断言，<strong>并且要证明它</strong>：引入回归、看它变红、再回退。
</Callout>

e2e 测试拥有自己的资源：在测试里创建，在 `afterEach` 里 dispose（**即使失败/重试/超时也要**）。共享 fixture 放在一个普通的 `tests/harness.ts` 里，**不要放在另一个 `*.e2e.ts` 里**——import 一个 spec 会重新注册它的 `describe`，把真实 API 调用翻倍。

`snapshot.yml` 声明 profile、组合/header 类别、录制策略、例外的回放或输入元数据，以及工作区事实。**类型化 token 保留父/子身份关系**；只有 header pin 拥有 prompt/schema 边车文件。一个会产生变更的场景**独立比对完整的 `workspace.expected/` 树**，而 record 与 refresh **从不重写**它。

  <strong>回放输入仍然有效</strong>用 <code>test:snapshot:refresh</code>。
  两种情况下都要<strong>审查每一处产生的 diff</strong>。fixture 在 macOS/Linux 上回放——
  <strong>修 fixture，不要修 normalizer</strong>。
</Callout>

## spec 的执行环境

<Callout variant="warn" title="只有进程是隔离的">
  端口、可预测的路径、外部命名空间与继承来的子进程<strong>都不隔离</strong>。
  fork 出来的 worker 会同时跑好几个 spec 文件，覆盖率门禁在它那个 job 里切成并发分区与其他门禁并列，自托管 runner 共享一台主机与一个卷。
</Callout>

所以：**通过它自己的 teardown 拥有每一个获取到的资源**；并且把「只有单独跑才通过」的 spec 读成**这个 spec 的缺陷**，而不是 runner 不稳定。

## 构建顺序不是任意的

```sh
tsc -b tsconfig.host.json
tsdown --env.DSH_BUILD_FACE host
tsc -b tsconfig.client.json
tsdown --env.DSH_BUILD_FACE client
pnpm run build:web
```

<Callout variant="note" title="Typert 只在 Host tsdown 期间运行">
  它由 <code>tsconfig.host.json</code> 播种，分析 Host 类型并生成 <strong>Host 反射产物</strong>与{' '}
  <strong>Host-for-Client 的 Remote 声明</strong>；<strong>Client tsdown 不启动 Typert</strong>。
  因此 <code>typecheck</code> 会在 Client tsc 之前跑完整的 Host lib 阶段。
</Callout>

tsdown 只消费前一个 tsc 阶段发到 `lib/types` 的 JavaScript。两次 tsdown 都用同一个完整的 workspace 匹配——它们**既不扫描构建产物来发现 Client 包，也不维护 Host/Client 包过滤列表**。

生成的 Host-for-Client Remote 声明是**故意留下的例外**：公开的 `typecheck`、`lint` 与 `doc-typecheck` 命令会先生成它们，而内部的 `*:contracts-ready` 脚本假定调用它的公开命令或调度门禁已经依赖了 Typert 合约生成或完整构建。

## 一个不熟悉的读者最容易低估的三条约定
